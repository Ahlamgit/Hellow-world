## Task 1A-01: RowVersion / Optimistic Concurrency

### Objective
Add SQL Server `rowversion` concurrency tokens to `ServiceRequests`, `BookingSlotReservations`, and `Coupons` so concurrent updates fail predictably instead of silently overwriting.

### Files to modify
| Layer | Files |
|-------|-------|
| Domain | `Khadamati.Domain/Entities/ServiceRequest.cs`, `BookingSlotReservation.cs`, `AdminEntities.cs` (Coupon) |
| Infrastructure | `Khadamati.Infrastructure/Data/Configurations/EntityConfigurations.cs`, `AdminEntityConfigurations.cs` |
| Infrastructure | New migration `AddRowVersionConcurrencyTokens` |
| Application | `Khadamati.Application/DTOs/Bookings/BookingDtos.cs` — expose `RowVersion` (byte[]) on read/update DTOs where clients must send it back |
| API | `BookingsController.cs` — accept optional concurrency token on mutating booking actions (reschedule, cancel, accept) |

### Database changes
```sql
-- Generated by EF migration (approximate)
ALTER TABLE ServiceRequests ADD RowVersion rowversion NOT NULL;
ALTER TABLE BookingSlotReservations ADD RowVersion rowversion NOT NULL;
ALTER TABLE Coupons ADD RowVersion rowversion NOT NULL;
```
- Configure `.IsRowVersion()` on each property in EF configurations.
- No data backfill required (`rowversion` auto-populates).

### API changes
- `BookingDto` gains optional `rowVersion` (base64) on GET responses.
- Mutating booking endpoints accept `rowVersion` in body; mismatch → **409 Conflict** with message to refresh.

### Web changes
- `src/web/src/services/api.ts` — include `rowVersion` on booking mutations.
- `BookingDetailPage.tsx`, `BookingWizardPage.tsx` — pass through token from loaded booking.

### Android changes
- `BookingDto` model + repository — store and send `rowVersion` on updates.

### iOS changes
- `Booking` model + `BookingsViewModel` — store and send `rowVersion` on updates.

### Tests to add/update
- Unit: concurrency conflict throws `ConflictException` when stale `RowVersion` submitted.
- Integration: two parallel reschedule attempts — one succeeds, one returns 409.

### Rollback plan
1. Revert migration (`dotnet ef database update <PreviousMigration>`).
2. Remove `RowVersion` properties from entities/DTOs.
3. Clients ignore unknown field (backward compatible if API stops sending it).

### Estimated implementation order
**1** (first task in 1A)

### Dependencies
- None (foundation for 1A-02, 1A-03)

|-------|-------|
| Application | **New** `ForbiddenException` in `Application/Common/Exceptions.cs` |
| Application | `PermissionAuthorizationHandler.cs` — fail with forbidden context |
| Application | `AdminAuthorization.cs` — throw `ForbiddenException` for missing permission |
| API | `ExceptionHandlingMiddleware.cs` — map `ForbiddenException` → 403 |
| API | `Program.cs` — configure JWT challenge vs forbid if needed |
| Tests | `ApiIntegrationTests.AdminAnalytics_WithoutReportsPermission_*` — expect **403** not 401 |

### Database changes
- None.

### API changes
- Permission-denied responses: HTTP **403** with `{ success: false, message: "..." }`.
- Unauthenticated: HTTP **401** (unchanged).

### Web changes
- `api.ts` interceptor — on 403, show "access denied" vs 401 "session expired".
- `AdminPageGuard.tsx` — handle 403 from API.

### Android changes
- `ApiClient` / auth interceptor — distinguish 401 (re-login) vs 403 (toast).

### iOS changes
- `APIClient` — same 401/403 distinction.

### Tests to add/update
- Integration: craftsman token → admin analytics → **403**.
- Unit: `ForbiddenException` middleware mapping.

### Rollback plan
- Revert to `UnauthorizedException` for permissions (restores 401 everywhere).

### Estimated implementation order
**8** (first in 1B)

### Dependencies
